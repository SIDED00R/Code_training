## 문제 설명

변수 쌍의 배열 equations와 실수 배열 values가 주어지며, equations[i] = [Ai, Bi]와 values[i]는 방정식 Ai / Bi = values[i]를 나타냅니다. 각 Ai 또는 Bi는 하나의 변수를 나타내는 문자열입니다.

또한 queries가 주어지며, queries[j] = [Cj, Dj]는 Cj / Dj = ?의 답을 구해야 하는 j^th 쿼리를 나타냅니다.

모든 쿼리에 대한 답을 반환하세요. 만약 특정한 답을 결정할 수 없다면, -1.0을 반환하세요.

참고: 입력은 항상 유효합니다. 쿼리를 계산할 때 0으로 나누는 경우가 발생하지 않으며 모순도 없다고 가정할 수 있습니다.

참고: 방정식 목록에 나타나지 않는 변수는 정의되지 않은 것이므로, 그에 대한 답은 결정할 수 없습니다.

 

예제 1:

입력: equations = [["a","b"],["b","c"]], values = [2.0,3.0], queries = [["a","c"],["b","a"],["a","e"],["a","a"],["x","x"]]
출력: [6.00000,0.50000,-1.00000,1.00000,-1.00000]
설명:
주어진 것: a / b = 2.0, b / c = 3.0
쿼리: a / c = ?, b / a = ?, a / e = ?, a / a = ?, x / x = ?
반환: [6.0, 0.5, -1.0, 1.0, -1.0 ]
참고: x는 정의되지 않음 => -1.0

예제 2:

입력: equations = [["a","b"],["b","c"],["bc","cd"]], values = [1.5,2.5,5.0], queries = [["a","c"],["c","b"],["bc","cd"],["cd","bc"]]
출력: [3.75000,0.40000,5.00000,0.20000]

예제 3:

입력: equations = [["a","b"]], values = [0.5], queries = [["a","b"],["b","a"],["a","c"],["x","y"]]
출력: [0.50000,2.00000,-1.00000,-1.00000]

 

제약 조건:

1 <= equations.length <= 20

equations[i].length == 2

1 <= Ai.length, Bi.length <= 5

values.length == equations.length

0.0 < values[i] <= 20.0

1 <= queries.length <= 20

queries[i].length == 2

1 <= Cj.length, Dj.length <= 5

Ai, Bi, Cj, Dj는 소문자 영문자와 숫자로 구성됩니다.

## 코드 리뷰

- 효율성: 효율적
- 시간복잡도: 그래프 구성 O(E), 쿼리당 DFS 탐색 O(V+E)이므로 전체 O(E + Q*(V+E)) ≈ O(Q*N) (N=equations 개수, V,E는 각각 O(N)). 공간복잡도는 O(V+E)
- 더 나은 알고리즘: 쿼리마다 그래프를 새로 순회하는 방식은 이미 이 문제에서 표준적으로 쓰이는 최적 접근입니다. 다만 쿼리 수가 매우 많고 변수(노드) 수가 적은 경우라면 Floyd-Warshall 방식으로 모든 노드 쌍의 비율을 O(V^3)에 미리 계산해두고 각 쿼리를 O(1)에 answer하는 방법이 더 유리할 수 있습니다. 반대로 변수가 매우 많고 쿼리가 적다면 현재 방식(쿼리별 DFS/BFS)이 가장 적합하며, Weighted Union-Find로 구현하면 병합 시점에 비율을 누적해 더 간결하게 처리할 수도 있습니다.

### 잘한 점

- 무방향 그래프와 역수 가중치를 활용해 쿼리별 DFS로 정답을 구하는 것은 이 문제에 대한 정석적이고 효율적인 접근입니다.
- defaultdict를 이용해 그래프에 존재하지 않는 변수에 대한 -1 처리를 간결하게 구현했습니다.
- 재귀 대신 명시적 스택을 사용한 반복적 DFS로 재귀 깊이 제한 문제를 회피했습니다.
- 무방향 그래프의 역방향 엣지를 활용해 'a/a' 같은 동일 변수 쿼리도 추가 분기 없이 자연스럽게 1.0으로 처리합니다.

### 개선할 점

- 자기 자신에 대한 쿼리(front==back) 처리가 명시적 조건문이 아니라 그래프의 역방향 엣지 존재에 암묵적으로 의존하고 있어 가독성과 유지보수성이 떨어집니다.
- weight를 defaultdict(int)로 선언했지만 모든 키가 명시적으로 채워지므로 일반 dict로도 충분하며 불필요한 선택입니다.
- 변수명(find, now_weight, now_node)과 로직에 대한 주석이 부족해 왜 올바르게 동작하는지 한눈에 파악하기 어렵습니다.
- front 또는 back이 그래프에 존재하지 않는 경우를 명시적으로 먼저 검사하지 않고 traversal 실패에 암묵적으로 의존하여 의도가 코드에 드러나지 않습니다.

### 상세 피드백

이 코드는 방향 그래프 대신 무방향 그래프(양방향 엣지)로 구성하고, 쿼리마다 DFS(스택 기반)로 목표 노드까지의 누적 곱을 구하는 전형적이고 효율적인 풀이입니다. 존재하지 않는 변수는 defaultdict가 빈 리스트를 반환하여 자연스럽게 -1로 처리되고, 특히 'a/a' 같은 자기 자신에 대한 쿈리도 무방향 그래프의 역방향 엣지를 이용해 1.0을 정확히 계산해내는 점이 인상적입니다. 다만 이 자기 자신 쿼리 처리가 명시적인 조건문이 아니라 그래프 구조에 우연히 의존하는 방식이라, 코드를 읽는 사람이 왜 올바르게 동작하는지 바로 이해하기 어렵고, 향후 그래프 표현을 바꾸면 버그가 될 위험이 있습니다. weight를 defaultdict(int)로 선언한 것도 실제로는 항상 명시적으로 값을 채워 넣기 때문에 불필요하며 일반 dict로 충분합니다. 변수명 find, now_weight, now_node 등은 의미는 전달되지만 다소 투박하고, 코드에 주석이 전혀 없어 핵심 로직(특히 자기 쿼리 처리)의 의도를 파악하기 어렵습니다. 전체적으로 알고리즘 선택과 복잡도는 이 문제의 제약 조건(≤20개 equations/queries)에 대해 충분히 효율적이며, DFS/BFS 태그에 부합하는 정석적인 풀이입니다.
