## 문제 설명

단일 연결 리스트의 head가 주어집니다. 이 리스트는 다음과 같이 나타낼 수 있습니다:

L0 → L1 → … → Ln - 1 → Ln

리스트를 다음과 같은 형태로 재배열하세요:

L0 → Ln → L1 → Ln - 1 → L2 → Ln - 2 → …

리스트 노드의 값은 수정할 수 없습니다. 노드 자체만 변경할 수 있습니다.

 

예제 1:

입력: head = [1,2,3,4]
출력: [1,4,2,3]

예제 2:

입력: head = [1,2,3,4,5]
출력: [1,5,2,4,3]

 

제약 조건:

리스트의 노드 개수는 [1, 5 * 10^4] 범위입니다.

1 <= Node.val <= 1000

## 코드 리뷰

- 효율성: 효율적
- 시간복잡도: 시간복잡도: O(N) (길이 계산 O(N) + 중간 지점 이동 O(N/2) + 후반부 역순 O(N/2) + 병합 O(N/2), 모두 합쳐도 O(N)) / 공간복잡도: O(1) (포인터 몇 개만 사용, 노드를 재배치할 뿐 별도 자료구조 없음)

### 잘한 점

- 길이 계산 후 미리 분할 지점을 정확히 구해 투 포인터(느린/빠른 포인터)로 중간을 찾는 방식보다 더 명확하고 홀/짝수 케이스를 (n+1)//2로 깔끔하게 통일 처리함
- O(N) 시간, O(1) 공간으로 추가 자료구조 없이 노드 자체만 재배치하여 문제의 'Only nodes themselves may be changed' 요구사항을 정확히 만족함
- 병합 단계에서 p1_next가 None인 홀수 길이 케이스를 if 분기로 처리해 NullPointerException 류의 버그를 방지함
- front_tail, second_head, p1/p2 등 역할이 명확히 드러나는 변수명을 사용함

### 개선할 점

- 코드 전체에 주석이 전혀 없어 길이 계산, 분할, 역순, 병합이라는 네 단계 로직을 처음 보는 사람이 파악하기 어려움
- head가 None인 극단적 입력(문제 제약상 N>=1이라 실제로는 발생하지 않음)에서 front_tail이 None이 되어 AttributeError가 발생할 수 있는 방어 코드가 없음
- n, front_len 등 변수명이 다소 추상적이어서 node_count, front_half_length처럼 더 구체적인 이름을 썼다면 가독성이 향상되었을 것
- 함수 초반에 head가 None이거나 단일 노드인 경우를 조기 반환(early return)으로 처리했다면 메인 로직의 복잡도를 줄일 수 있었음

### 상세 피드백

이 풀이는 Reorder List 문제에 대해 이론적으로 최적인 접근을 사용했습니다. (1) 전체 노드 개수를 세어 중간 지점을 정확히 계산하고, (2) 리스트를 전반부/후반부로 분리한 뒤 후반부를 in-place로 역순 연결하고, (3) 두 포인터를 이용해 전반부와 역순된 후반부를 교대로 병합하는 3단계 구조입니다. 전체 과정이 노드를 한 번씩만 순회하므로 O(N) 시간에 수행되고, 추가 메모리는 상수 개의 포인터뿐이므로 O(1) 공간입니다. 이는 스택이나 배열에 노드를 저장해 O(N) 공간을 쓰는 해법보다 메모리 효율이 뛰어나며, LeetCode Medium 난이도에 걸맞은 깔끔한 투 포인터 + 링크드 리스트 조작 기법을 잘 보여줍니다. front_len 계산과 병합 루프에서 p1_next가 None인 경우(홀수 길이 리스트의 마지막 전반부 노드)를 조건문으로 분기해 널 포인터 참조를 방지한 점도 섬세합니다. 다만 각 단계(길이 측정, 분할, 역순, 병합)에 대한 주석이 전혀 없어 처음 읽는 사람이 로직을 따라가기 쉽지 않고, head가 None인 경우(문제 제약상 발생하지 않지만) front_tail이 None이 되어 AttributeError가 날 수 있는 잠재적 취약점이 있습니다. 전반적으로 효율성과 정확성 측면에서 매우 우수한 풀이입니다.
