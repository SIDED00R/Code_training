## 문제 설명

당신은 멋진 부모이고 아이들에게 쿠키를 주고 싶다고 가정합니다. 단, 각 아이에게는 최대 한 개의 쿠키만 줄 수 있습니다.

각 아이 i는 욕심 지수 g[i]를 가지고 있으며, 이는 그 아이가 만족할 수 있는 쿠키의 최소 크기를 의미합니다. 그리고 각 쿠키 j는 크기 s[j]를 가지고 있습니다. 만약 s[j] >= g[i]라면, 쿠키 j를 아이 i에게 줄 수 있고, 아이 i는 만족하게 됩니다. 당신의 목표는 만족하는 아이의 수를 최대화하여 그 최대 개수를 출력하는 것입니다.

 

예제 1:

입력: g = [1,2,3], s = [1,1]
출력: 1
설명: 아이는 3명이고 쿠키는 2개입니다. 3명의 아이의 욕심 지수는 각각 1, 2, 3입니다.
쿠키가 2개 있지만, 두 쿠키의 크기가 모두 1이기 때문에 욕심 지수가 1인 아이만 만족시킬 수 있습니다.
따라서 1을 출력해야 합니다.

예제 2:

입력: g = [1,2], s = [1,2,3]
출력: 2
설명: 아이는 2명이고 쿠키는 3개입니다. 2명의 아이의 욕심 지수는 각각 1, 2입니다.
쿠키가 3개 있고 그 크기가 모든 아이를 만족시킬 만큼 충분히 크므로,
2를 출력해야 합니다.

 

제약 조건:

1 <= g.length <= 3 * 10^4

0 <= s.length <= 3 * 10^4

1 <= g[i], s[j] <= 2^31 - 1

 

참고: 이 문제는 다음과 동일합니다:  2410: Maximum Matching of Players With Trainers.

## 코드 리뷰

- 효율성: 효율적
- 시간복잡도: O(N log N + M log M) 시간, O(N + M) 공간 (N=g 길이, M=s 길이)

### 잘한 점

- 정렬 기반 그리디 접근으로 이론적 최적 시간복잡도(O(N log N + M log M))를 달성함
- 빈 리스트(s가 비어있는 경우 등) 엣지 케이스를 while 조건으로 자연스럽게 처리함
- sorted()를 사용해 원본 입력 리스트를 변경하지 않는 안전한 구현
- 타입 힌트를 명시하여 코드 가독성에 신경 씀

### 개선할 점

- 내림차순 정렬 후 리스트 끝에서 pop하는 방식이 사실상 오름차순 투 포인터를 우회적으로 구현한 것이라 의도 파악이 쉽지 않음
- list.pop()을 반복 호출하는 대신 인덱스 변수(i, j)를 사용하는 전통적인 투 포인터 방식이 더 직관적이고 일반적인 관례에 부합함
- answer 변수명이 greedy 매칭의 의미(매칭된 아이 수 등)를 더 구체적으로 드러내는 이름(예: matched_count)이었다면 가독성이 더 좋았을 것

### 상세 피드백

이 문제는 그리디 + 정렬 조합이 이론적으로 최적인 풀이이며, 제출 코드는 정확히 이 접근을 사용하고 있습니다. g와 s를 각각 정렬(O(N log N), O(M log M))한 뒤 한 번의 선형 스캔(O(N+M))으로 매칭을 완료하므로 전체 시간복잡도는 정렬이 지배하는 O(N log N + M log M)이며, 이보다 더 빠른 알고리즘은 존재하지 않습니다(정렬되지 않은 입력을 다뤄야 하므로). 다만 구현 방식에서 내림차순으로 정렬한 뒤 리스트의 끝에서 pop()을 하여 사실상 '가장 작은 값끼리 비교'하는 오름차순 투 포인터를 흉내 내고 있는데, 이는 결과적으로는 맞지만 코드를 읽는 사람이 한 번 더 생각해야 하는 우회적인 방식입니다. sort_g.sort()와 sort_s.sort()를 오름차순으로 정렬하고 인덱스 변수 i, j를 증가시키는 전통적인 투 포인터 방식이 의도를 더 명확하게 드러냅니다. 또한 reverse=True 정렬과 pop(-1) 조합은 내부적으로 reversed() 호출이나 슬라이싱 오버헤드가 약간 더 들 수 있어(비록 Big-O는 동일) 미세하게 비효율적입니다. 전반적으로 정답을 정확히 도출하며 효율성 면에서는 문제가 없으나, 가독성과 관례적인 구현 스타일 측면에서 개선 여지가 있습니다.
