## 문제 설명

길이가 각각 m과 n인 두 문자열 s와 t가 주어졌을 때, t의 모든 문자(중복 문자 포함)를 포함하는 s의 최소 윈도우 부분 문자열을 반환하라. 그러한 부분 문자열이 없다면, 빈 문자열 ""를 반환하라.

테스트 케이스는 답이 유일하도록 생성된다.

 

예제 1:

입력: s = "ADOBECODEBANC", t = "ABC"
출력: "BANC"
설명: 최소 윈도우 부분 문자열 "BANC"는 문자열 t의 'A', 'B', 'C'를 포함한다.

예제 2:

입력: s = "a", t = "a"
출력: "a"
설명: 문자열 s 전체가 최소 윈도우이다.

예제 3:

입력: s = "a", t = "aa"
출력: ""
설명: t의 'a' 두 개 모두 윈도우에 포함되어야 한다.
s의 가장 큰 윈도우에는 'a'가 하나밖에 없으므로, 빈 문자열을 반환한다.

 

제약 조건:

m == s.length

n == t.length

1 <= m, n <= 10^5

s와 t는 대문자와 소문자 영어 알파벳으로 구성된다.

 

심화 문제: O(m + n) 시간에 동작하는 알고리즘을 찾을 수 있는가?

## 코드 리뷰

- 효율성: 보통
- 시간복잡도: 핵심 슬라이딩 윈도우 로직(deque push/pop)은 각 문자가 최대 한 번씩만 들어오고 나가므로 O(m) 상각이지만, 윈도우가 개선될 때마다 '' .join(q)로 문자열을 통째로 재구성하기 때문에 이 부분이 최악의 경우 O(m) 비용을 여러 번 반복시켜 전체적으로 O(m^2)까지 악화될 수 있습니다. 공간복잡도는 check(Counter)가 O(k)(k = t의 고유 문자 수, 최대 52), deque가 현재 윈도우 크기만큼 O(m)을 차지합니다.
- 더 나은 알고리즘: deque 전체를 유지하고 join으로 문자열을 매번 재구성하는 대신, s에 대해 left/right 두 정수 포인터만 이동시키며 윈도우 내 문자 빈도(고정 크기 배열 또는 Counter)와 '현재 몇 개의 고유 문자가 만족되었는지'만 추적하는 표준 Minimum Window Substring 패턴을 쓰는 것이 더 적합합니다. 최적 윈도우를 찾을 때는 (start_index, length) 같은 정수 쌍만 갱신하고, 루프가 끝난 뒤 s[start:start+length]로 딱 한 번만 슬라이싱하면 진짜 O(m+n) 시간, O(1)~O(52) 추가 공간으로 구현할 수 있습니다.

### 잘한 점

- 필요 문자 수를 모두 채운 뒤에만 왼쪽을 줄이고, 유효성이 깨지기 직전 상태를 후보로 기록하는 shrink 로직을 정확히 구현해 중복 문자가 있는 t 케이스도 올바르게 처리함
- Counter와 counter(고유 문자 만족 개수) 두 단계로 나눠 조건 체크를 O(1)에 수행하도록 설계한 점은 표준 sliding window 패턴의 핵심을 잘 따르고 있음

### 개선할 점

- s를 인덱스로 직접 다루지 않고 deque에 문자를 복사해 넣은 뒤, 개선이 일어날 때마다 '' .join(q)로 문자열을 재구성하므로 불필요한 오버헤드가 있고 최악의 경우 시간복잡도가 O(m^2)까지 악화될 위험이 있음
- 변수명(q, out, alp, check, counter)이 역할을 직관적으로 드러내지 못해 로직을 따라가기 어렵고, start/length 인덱스만 추적하는 표준 구현에 비해 코드가 불필요하게 복잡함

### 상세 피드백

주어진 예제들에 대해 직접 트레이싱해본 결과 알고리즘 자체의 로직(필요 문자 수를 모두 만족했을 때부터 왼쪽을 줄여가며 유효성을 깨기 직전까지 후보로 기록)은 정확하게 동작하며, 중복 문자가 있는 t(예: "aa")도 올바르게 처리합니다. 다만 s를 직접 인덱싱하지 않고 deque에 문자를 하나씩 복사해 넣고, 윈도우를 축소할 때마다 '' .join(q)로 전체 문자열을 다시 조립하는 방식은 불필요한 오버헤드입니다. 특히 join 호출은 개선이 일어날 때마다 실행되는데, 이론적으로 윈도우 크기가 큰 상태에서 여러 번 개선이 반복되는 입력이 주어지면 O(m^2)에 가까운 시간이 걸릴 수 있어 Hard 난이도에서 요구하는 O(m+n) 목표에는 못 미칩니다. s의 원본 인덱스를 그대로 활용해 포인터만 옮기는 표준 투 포인터 구조로 바꾸면 코드도 더 짧아지고 성능도 보장됩니다. 변수명(q, out, alp, check, counter)도 의미가 바로 드러나지 않아 가독성이 떨어지는 편입니다.
