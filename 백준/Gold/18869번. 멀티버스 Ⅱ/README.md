## 문제 설명

M개의 우주가 있고, 각 우주에는 1부터 N까지 번호가 매겨진 행성이 N개 있다. 행성의 크기를 알고 있을때, 균등한 우주의 쌍이 몇 개인지 구해보려고 한다. 구성이 같은데 순서만 다른 우주의 쌍은 한 번만 센다.
두 우주 A와 B가 있고, 우주 A에 있는 행성의 크기는 A_1, A_2, ..., A_N, 우주 B에 있는 행성의 크기는 B_1, B_2, ..., B_N라고 하자. 두 우주의 행성 크기가 모든 1 ≤ i, j ≤ N에 대해서 아래와 같은 조건을 만족한다면, 두 우주를 균등하다고 한다.
A_i < A_j → B_i < B_j
A_i = A_j → B_i = B_j
A_i > A_j → B_i > B_j

## 입력

첫째 줄에 우주의 개수 M과 각 우주에 있는 행성의 개수 N이 주어진다. 둘째 줄부터 M개의 줄에 공백으로 구분된 행성의 크기가 한 줄에 하나씩 1번 우주부터 차례대로 주어진다.

## 출력

첫째 줄에 균등한 우주의 쌍의 개수를 출력한다.

## 코드 리뷰

- 효율성: 보통
- 시간복잡도: O(M * N log N) (줄마다 좌표 압축 O(N log N) + BIT 연산 O(N log N), 시그니처 길이 2N인 튜플 해싱/비교 포함)
- 더 나은 알고리즘: 각 줄을 '좌표 압축(coordinate compression)'하여 얻은 랭크 배열(rank array) 자체를 시그니처로 사용하면 충분합니다. 두 우주가 균등하다는 조건(Ai<Aj→Bi<Bj, Ai=Aj→Bi=Bj, Ai>Aj→Bi>Bj)은 정확히 '동일한 값에는 동일한 랭크, 다른 값 사이의 대소관계도 랭크로 그대로 보존'되는 것과 동치이기 때문입니다. 즉 sorted(set(line))로 unique 값을 구하고 각 원소를 rank로 바꾼 길이 N짜리 튜플만 Counter에 넣으면 BIT나 seen 배열 없이도 동일한 결과를 얻을 수 있고, 코드가 훨씬 단순해집니다. (참고 태그: 정렬, 값/좌표 압축)

### 잘한 점

- 두 우주가 균등하다는 조건을 '상대적 순서 구조를 시그니처로 추출해 그룹화'하는 핵심 아이디어로 정확히 환원해 구현함
- sys.stdin.readline과 Counter를 활용해 입력 처리와 그룹 집계를 효율적으로 처리함
- BIT(펜윅 트리)를 이용해 각 원소보다 작은 값의 개수를 O(log N)에 계산하는 등 자료구조 활용 능력을 보여줌

### 개선할 점

- 좌표 압축으로 얻은 rank 배열 자체가 균등성 판정에 충분한 시그니처인데, BIT와 seen 배열로 (less, equal) 쌍을 계산하는 불필요하게 복잡한 구현을 사용함
- equal(같은 값의 등장 순서) 정보는 균등 조건 판정과 무관한데도 시그니처에 포함되어 튜플 길이가 2N으로 늘어나 해싱/비교 비용이 증가함
- 매 줄마다 BIT와 seen 배열을 새로 생성해 메모리/초기화 오버헤드가 추가로 발생함
- for문과 while문에서 변수명 i를 반복 재사용해 코드 가독성을 다소 떨어뜨림

### 상세 피드백

이 풀이는 문제의 본질—'두 우주가 균등하다'는 것은 결국 상대적 순서 구조가 동일하다는 것—을 정확히 이해하고, 이를 시그니처로 변환해 Counter로 그룹화한 뒤 쌍의 개수를 세는 올바른 전략을 취하고 있습니다. BIT를 사용해 각 원소 앞에 자신보다 작은 값의 개수(less)와 같은 값이 이미 몇 번 나왔는지(equal)를 계산해 (less, equal) 쌍으로 시그니처를 만드는데, 이는 정확하지만 사실상 과잉 설계입니다. 좌표 압축으로 얻은 rank 값 자체가 이미 '작은/같은/큰' 관계를 완전히 표현하므로, rank 배열만으로도 동일한 시그니처 역할을 할 수 있습니다. 또한 equal 카운트(같은 값의 등장 순서)는 균등 조건 판정에 전혀 필요하지 않은 정보로, 불필요하게 시그니처 길이를 2배로 늘리고 튜플 해싱/비교 비용을 증가시킵니다. 매 줄마다 BIT와 seen 배열을 새로 할당하는 것도 추가 오버헤드입니다. 결과적으로 시간복잡도 자체는 단순 정렬 기반 풀이와 같은 O(N log N) 오더이지만, 상수 배와 구현 복잡도 면에서 손해를 보는 '정답이지만 과한' 풀이입니다. N, M 범위가 작다면 (이 문제 제약 상 M≤50, N≤1000 수준) 실행 시간에는 문제가 없지만, 대회 코드로서의 간결성과 가독성 측면에서는 개선 여지가 큽니다.
