## 문제 설명

M개의 우주가 있고, 각 우주에는 1부터 N까지 번호가 매겨진 행성이 N개 있다. 행성의 크기를 알고 있을때, 균등한 우주의 쌍이 몇 개인지 구해보려고 한다. 구성이 같은데 순서만 다른 우주의 쌍은 한 번만 센다.
두 우주 A와 B가 있고, 우주 A에 있는 행성의 크기는 A_1, A_2, ..., A_N, 우주 B에 있는 행성의 크기는 B_1, B_2, ..., B_N라고 하자. 두 우주의 행성 크기가 모든 1 ≤ i, j ≤ N에 대해서 아래와 같은 조건을 만족한다면, 두 우주를 균등하다고 한다.
A_i < A_j → B_i < B_j
A_i = A_j → B_i = B_j
A_i > A_j → B_i > B_j

## 입력

첫째 줄에 우주의 개수 M과 각 우주에 있는 행성의 개수 N이 주어진다. 둘째 줄부터 M개의 줄에 공백으로 구분된 행성의 크기가 한 줄에 하나씩 1번 우주부터 차례대로 주어진다.

## 출력

첫째 줄에 균등한 우주의 쌍의 개수를 출력한다.

## 코드 리뷰

- 효율성: 보통
- 시간복잡도: O(M * N log N) 시간, O(M * N) 공간 (각 우주마다 길이 2N짜리 시그니처를 저장)
- 더 나은 알고리즘: 문제의 동치 조건(Ai<Aj → Bi<Bj 등)은 결국 '각 원소를 중복을 허용한 순위(dense rank)로 바꾼 수열이 완전히 동일한가'와 같습니다. 따라서 각 우주마다 sorted(set(line))로 좌표 압축을 한 뒤 rank[v] 값만으로 구성된 튜플을 시그니처로 사용하면 충분합니다. 펜윅 트리로 prefix 내에서의 less/equal 개수를 매번 계산할 필요가 없고, O(N log N) 정렬 한 번으로 모든 정보가 결정됩니다. 결과적으로 로그 팩터와 트리 생성/질의 오버헤드, 그리고 시그니처 길이(2N→N)를 모두 줄일 수 있습니다.

### 잘한 점

- 펜윅 트리를 이용해 삽입 순서에 따른 상대적 순위(less/equal)를 정확히 계산하는 아이디어를 구현했고, 이는 동치 조건을 올바르게 포착함
- Counter를 이용해 시그니처별 그룹 개수를 구하고 조합 공식(nC2)으로 답을 구하는 전체 로직 흐름이 명확하고 정확함
- sorted(set(line))을 통한 좌표 압축 자체는 올바르게 적용됨

### 개선할 점

- 핵심 동치 조건은 '좌표 압축된 순위 수열이 동일한가'로 단순화 가능한데, 불필요하게 펜윅 트리를 매 우주마다 새로 생성하여 계산 비용과 코드 복잡도를 늘림
- 시그니처를 (less, equal) 쌍으로 구성해 길이가 2N이 되므로, 단순 rank 튜플(길이 N)을 쓰는 것보다 메모리와 해시 비교 비용이 두 배가 됨
- 변수명(now_node 등)이 트리 순회 코드에서 가져온 듯한 이름이라 그래프 노드가 아닌 '행성 값'이라는 문맥과 맞지 않아 가독성을 다소 떨어뜨림
- 입력 크기(M, N)의 제약에 대한 고려나 엣지 케이스(N=1, 모든 값이 동일한 경우 등)에 대한 별도 검증/주석이 없음

### 상세 피드백

이 코드는 각 우주를 펜윅 트리를 이용해 원소를 하나씩 삽입하면서 '현재까지 삽입된 원소 중 자신보다 작은 개수(less)'와 '같은 개수(equal)'를 누적한 뒤, 이 두 값을 번갈아 쌓은 길이 2N짜리 튜플을 우주의 '시그니처'로 사용합니다. 이 시그니처가 같으면 두 우주가 균등하다고 보고 Counter로 묶어 조합(nC2)을 더하는 방식인데, 이 접근은 정답은 맞지만 다소 과한 설계입니다. 문제의 동치 조건은 사실 '좌표 압축된 순위 수열이 동일한가'와 완전히 같은 문제이기 때문에, 펜윅 트리 없이 sorted(set(line))로 만든 rank 딕셔너리만으로 rank 튜플을 만들어 바로 Counter에 넣어도 충분합니다. 현재 구현은 알고리즘적으로는 맞지만 (1) 매 우주마다 펜윅 트리 객체(클로저)를 새로 생성하는 오버헤드, (2) 시그니처 길이가 N이 아니라 2N이 되어 메모리/해싱 비용이 두 배가 되는 비효율, (3) O(log N) 만큼의 불필요한 질의 연산이 추가되는 문제가 있습니다. N, M이 크지 않다면(백준 제한상 보통 수백~수천 수준) 문제없이 통과하겠지만, 더 간단하고 가벼운 방법이 명확히 존재하므로 'ok' 수준으로 평가합니다. 또한 입력 크기가 커질 경우 파이썬에서 클로저 기반 펜윅 트리 생성 비용이 누적되어 시간 초과 위험이 있을 수 있는 점도 고려해야 합니다.
